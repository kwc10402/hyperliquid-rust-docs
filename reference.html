A node rebuilt from evidence

HLX is a Rust reimplementation of HyperCore and HyperEVM. Its progress is measured against native execution, state and wire evidence, with each claim tied to a specific scope.

Reproduce the machine, including its boundaries

The project reconstructs the state machine behind Hyperliquid's exchange and EVM node. An implementation must reproduce successful transitions, rejected actions, emitted responses, persistent state and consensus encodings. A plausible trading engine is insufficient when another node commits to different bytes.

The research method starts with an identified native binary, follows its bounded control flow, implements the recovered behavior and checks forward execution against native checkpoints. Native outputs serve as comparison targets; copying those outputs into the candidate does not establish independent execution.

Current model: official Mainnet 113

The native coverage snapshot is dated October 9, 2026. This documentation was refreshed October 11. The model is official Mainnet index 113, bound to SHA-256 67cc6e8a0674b371cfeda73f6d772003ab2a2c4e4d6cd90fbc09190a2cc52c68. Historical testnet and earlier mainnet packets retain their original scope.

Current mainnet integration includes 42 W2 state slots, a 60-field exchange ABCI tree, separate L1-hash and ABCI-digest votes and trackers, oracle caps and guards, a funding outer cap of ±0.04, EVM deletion handling, queued native-token transfers and an 80-subaccount admission limit.

The website describes a dated implementation and evidence snapshot. It does not claim that every native branch is implemented or that the project has achieved production node equivalence.

What the bounded successes establish

The October 8 integration record reports an original 10,000-block mainnet interval matching all 909 supplied response hashes, all ten 60-field native checkpoints and all three full EVM accumulators. Later repair packets preserve and extend specific passing windows. These are results for identified inputs and executable identities.

The longer 500,000-block attempt stopped with persistent divergence. The October 9 audit records a 45-checkpoint contiguous exact prefix, no terminal summary and no terminal exit record. Live synchronization also remains uncertified. Independent passing windows cannot be assembled into a continuous-run certificate.

Ownership across seventeen crates

The workspace separates exchange execution, EVM execution, wire transport, consensus and research tooling. Crate presence does not imply that every advertised integration is complete.

The exchange is the execution owner

hl-engine owns Exchange: order books, clearinghouse accounts, collateral routes, funding, lending, staking and hash production. hl-evm supplies the revm executor, checkpoint database integration, read precompiles and CoreWriter extraction. hl-node assembles those owners into bootstrap, authenticated application and replay commands.

Keeping these responsibilities explicit matters at every boundary. Transport decodes a record; consensus authenticates its certificate; the applier advances owned execution; the engine publishes state; the EVM executor commits its database changes. A transport observation or a generic pipeline checkpoint is not equivalent to successful exchange application.

Trace a concrete caller before assigning capability

The primary observe-only node command is node-run. It uses self_boot, attaches the EVM checkpoint, constructs a ClientBlockAuthenticator and invokes the committed applier. Legacy follower and devnet paths have different lifecycles and must be reviewed separately.

Some reusable surfaces remain scaffolding. The stage state writer tracks roots without implementing QMDB persistence, and stage unwind does not revert exchange state. The RPC server has an atomics-only mode and an exchange-backed mode. The BFT backend interface does not establish that alternative consensus algorithms are implemented.

A complete architectural claim needs the actual command, constructor, owner and failure path. Counting interfaces, dispatch arms or crates cannot substitute for that trace.

Types make ownership reviewable

The engineering direction is typed actions and state, one writer per fact and exact representations at consensus boundaries. A mutation may affect a runtime view, snapshot mirror, tracker and hash slot together; those effects belong in one writer rather than competing maps.

The October 9 typed audit covered a 733-file Rust snapshot across these crates, while the current tracked-file inventory has 732 Rust files. These are different inventories. The audit found concrete debt in governance sidecars, order re-encoding, paired EVM representations and weak identifier domains; its lexical occurrence count is not a defect count or completion measure.

ExEx is HLX-specific post-execution tooling

Execution extensions were added to HLX; the native binary does not provide this ExEx feature. The node forwards runtime observer events to logging, research and indexing subscribers. Some engine events are emitted during execution; the observers do not feed their outputs back into consensus state. These notifications are observers of execution, not consensus state or a missing native protocol feature.

Delivery is best effort. Both the node's event bridge and the extension manager use bounded broadcast channels with capacity 16,384. On Lagged(n), the bridge and indexer log the skipped count and continue without backfill. The disk event index can therefore contain gaps while the indexing task keeps running.

An ExEx index is not a complete event journal. Durable delivery, acknowledged cursors and backfill would be a separate HLX extension design, not a repair to native execution parity.

From authenticated input to published state

Execution order determines counters, queue maturity, book state and hashes. Reproducing each operation with a different surrounding phase order can still diverge.

Authenticate before mutating the exchange

Live ClientBlocks admission validates the block sequence, transaction correspondence, proposer and certificates before producing the token accepted by the live applier. The final commit proof authenticates the batch; intermediate records have their own framing constraints. The authenticated record is borrowed so callers cannot change its bytes after admission.

Signature recovery alone is insufficient. The verifier also needs the appropriate historical stake sample and valid certificate links. Advancing an observed round, parsing a block or matching a transaction hash cannot replace this admission boundary.

The current native driver has several owners

The Mainnet 113 driver enters begin-block work, completes transaction-index reset, then takes matured delayed rows and executes them. It prepares incoming batches, dispatches actions, forwards post-batch outputs, schedules W2 hashing and runs notification and periodic-tree adapters. These are separately recorded native phases.

The begin-block profiler descriptors order funding distribution, funding-rate updates, aggressive cancellation at the OI cap, empty-state pruning, recent-OI reset, stale main-oracle refresh, stale HIP-3 mark refresh and BOLE liquidation. A descriptor pins an interval and name; its mutation callees still require their own proof.

The source's named effect enum is a useful implementation grouping. It is not the complete native driver and should not be promoted into a universal nine-step protocol diagram.

An action changes more than its central account

Action execution can reserve admission capacity, recover the actor, enter a collateral route, modify a book, update balances and trackers, emit a response and queue cleanup. Success and failure paths can differ in which rows become visible. Creating a missing row simply to make a hash agree can change the next action's lookup behavior.

Delayed actions, trigger activation, staking maintenance and end-of-block cleanup share these writers but arrive through different callers. A repair must preserve the caller's ordering, response shape and accounting domain, including an unchanged or empty result that still has publication effects.

Execution completion includes publication

The exchange, EVM database, history and execution cursor must describe the same committed progress. Publishing a cursor before a later fallible step leaves a restart or downstream reader with a misleading view of completion.

The October 9 system audit identified ordering and durability risks around EVM commits, leader-input synchronization and checkpoint readiness. Subsequent source work includes publication and pairing repairs, but those changes require their own validation. A static source repair is not a restart or fault-injection certificate.

Action identity, dispatch and response

Wire names, physical native entries, Rust variants and emitted responses are distinct identities. The current action inventory preserves their explicit bindings.

What the 92-action inventory counts

The current bounded native inventory contains 92 physical outer entries with 92 names. All names bind to exact Rust serde spellings. The source declares 110 variants, including source-only, historical and scaffolded surfaces. Those denominators answer different questions and cannot be combined into a completeness ratio.

The inventory records native serializer and dispatcher addresses, source declarations and dispatch arms, directly resolved helpers, guard snippets and hashes. It leaves every action's complete implementation, executed tests and runtime parity unreviewed. A packet address reference is useful provenance, not whole-handler acceptance.

Families share infrastructure, not identical semantics

Order and cancellation actions use book and clearinghouse writers. Transfers route spot or class collateral. Margin actions change isolated allocations or leverage. Staking, bridge, governance, deployment, lending and outcome actions maintain additional state machines through the same signed-action surface.

Typed ApplyAction implementations own many family handlers, while other variants use dedicated methods or special dispatcher branches. Inner variants need their own payload and tag proofs. The number of trait implementations is not an additional set of actions and does not certify nested dispatch.

An accepted action does not always emit the same envelope

Response production belongs to the recovered action path. Some transitions emit a default status, some carry order statuses or fills, and some succeed without an ordinary response envelope. Ledger deltas and response envelopes are also separate outputs. A generic success response can change resps.Hash even when the central state mutation looks correct.

Nine type_name values differ from the current native and serde names. A dated devnet audit found that producer and consumer string disagreement can hide a rejection behind default success. This is a concrete mapping issue; no native response-hash defect was demonstrated by that static audit.

Preserve original signing bytes and exact action names. Re-encoding a normalized JSON object can change field order, omitted values or the signed preimage.

Admission limits and unsupported behavior stay explicit

The Mainnet 113 integration includes an 80-subaccount admission limit and queued native-token transfers. Such limits and timing changes belong to the current model, not a runtime compatibility switch selected by height or environment.

The 61 rows containing visible guard candidates are conditional syntax findings. A guard may reject an invalid native input or sit behind a branch current mainnet never permits. The remaining 31 rows are unreviewed. An unsupported execution diagnostic must remain distinguishable from a native business rejection and must not invent compensating state.

Books, fills and mutation chronology

Matching combines ordered books with admission, spend limits and accounting. Native arena and tracker chronology matter even when prices and final balances appear equal.

A book has more structure than its price levels

OrderBook maintains bid and ask levels, a stable slot arena, an order-ID index and user state. Levels reference arena records rather than owning independent copies. The main matching surface uses price-time priority, with additional native priority metadata carried where the model requires it.

Snapshot wire order, live matching order and auxiliary indexes must remain consistent. An arena release, index unlink and tracker update can affect future behavior differently from deleting one visible order row. Sorting records after a mutation is not a substitute for reproducing the native writer's order.

Fill eligibility includes the funding route

Before a taker consumes liquidity, the engine checks asset configuration, order shape, margin or spend capacity and account routing. Reduce-only constraints restrict exposure, while time-in-force governs whether an unmatched remainder can rest. Trigger and modify actions add their own identity and activation rules.

A fill moves several views: cash or token balances, position size and entry notional, fees, order remainder, holds, open-order tracking and response data. Maker and taker transitions must occur in the recovered sequence. Equal aggregate PnL does not prove that per-account rounding or first-touch publication agrees.

Publication can be the defect after matching succeeds

The book-publication acceptance packet covers original-quantity publication and trigger activation sequencing over specified mainnet windows. These repairs address what the native book and user tracker expose after an operation, rather than changing a market-level matching formula.

A separate ordered-tracker audit identified a trigger child reserved before reduce-only capacity cleanup in native code. Reversing those phases changes owner asset-vector chronology. Its causal input and column controls are recorded, but the dated coverage ledger still labels that repair pending until its own gates close.

Special paths reuse books with additional semantics

Spot placement must respect live spend-token budgets and holds. Complementary outcomes can consume liquidity from another book and translate prices into the incoming order's terms. Liquidation and backstop callers can also enter shared financial writers while retaining different admission and publication contracts.

Validate a matching change with statuses, fills, order IDs and next-state checkpoints. For a performance change, compare every per-block response and final-state identity against a bound baseline. The source contains allocation and indexing optimizations, but this site makes no unmeasured throughput or latency claim.

Collateral, account classes and liquidation

Margin is a state transition problem: accounts, positions, reserves and collateral routes jointly determine admission and liquidation. Exact representations and writer order are part of that result.

Account value and available capacity are different quantities

The clearinghouse tracks class cash, positions, leverage and open-order obligations. Valuation combines those facts with the appropriate mark or oracle view and margin tiers. Initial admission capacity and maintenance liquidation capacity answer different questions; a positive displayed balance alone does not establish that an order is admissible.

Funding settlement writes cash and position funding state through its own owner. Margin calculations must follow that settlement model rather than introducing an additional pending-funding term from a conventional formula. The applicable price, amount scale and deduction come from the native producer for that field.

Cross, isolated and portfolio paths have distinct routes

Cross margin draws on class-wide collateral; isolated margin maintains a position allocation and stricter update rules. Asset modes can block new exposure or require isolated treatment. Leverage changes and isolated top-ups preserve native rejection order, including empty positions, zero updates and restricted removal.

Portfolio accounts can move collateral through spot endpoints, class cash and BOLE supply or borrow shares. An action may fund its operation before the core and release or repay collateral afterwards. These routes are shared writers, not opportunities to patch only the balance map visible to a test.

Stored quantities and arithmetic kernels are separate contracts

Spot and EVM amounts require exact wide integer carriers; collateral and cash commonly use scaled integers; prices and sizes use field-specific decimal representations. Mainnet serializes designated amount values as scalars, while internal unit information still guides correct mutation.

Exact storage does not imply replacing every native floating-point operation with decimal arithmetic. Position entry transitions have distinct producers: same-sign increases, opens or flips, full closes and partial reductions. Where the native reduction divides sizes, multiplies old entry and truncates, operation order and binary64 rounding must be preserved.

Qualification, planning and execution must remain distinct

Liquidation first qualifies an account using the relevant valuation and margin mode. A planner can return no plan, a rebuilt plan, an invalid valuation or executable operations. The caller then selects the correct accounting and publication domain. Ordinary dex liquidation, portfolio liquidation and lending liquidation share parts without sharing every terminal result.

The portfolio financial acceptance packet certifies described branches and windows. It does not certify every liquidation mode, backstop path or lending begin-block owner. Track the remaining callers and error paths separately, especially when a proposed refactor returns unsupported at a branch whose native terminal behavior is already known.

Funding samples and cash settlement

Funding separates premium sampling, rate production and settlement. Snapshot-carried multipliers and interest rates remain live state; the current outer cap comes from immutable startup rules.

Premium production depends on current inputs

Each perpetual class has funding-tracker state for premium samples, impact notional, clamp behavior, multipliers and interest rates. Rate production consumes that tracker rather than a single universal constant. Oracle freshness and the carried sampling state affect which new sample enters the calculation.

Loading a price from a snapshot must not mark it as a newly received oracle update. The runtime distinguishes carried prices from fresh writes so bootstrap cannot create a premium-ring event that native execution never observed.

The cap is applied before period scaling

For the clamped funding path, the rate combines premium with a clamped interest-minus-premium adjustment, applies the relevant multiplier, clamps the outer eight-hour rate and then scales to the funding period. The current Mainnet 113 outer cap is ±0.04. Moving the clamp after scaling changes the result.

Other tracker flags and class parameters remain part of the native computation. The formula below describes the corresponding clamped path; it is not a replacement for inspecting each tracker mode and its precise arithmetic.

centered = clamp(interest - premium, -inner_cap, +inner_cap)
rate_8h = clamp((premium + centered) * multiplier, -0.04, +0.04)
rate_1h = rate_8h / 8

Settlement writes account state

Funding distribution uses cumulative funding differences, position size and the appropriate oracle valuation to update cash and funding entries. Its bucket guard and chronological placement determine when that transition happens. Funding-rate refresh is a separate phase and does not itself settle every account.

Tests must cover zero and nonzero positions, rounding, class collateral, carried cumulative values and the due or not-due guard. Forward checkpoints verify that cash, positions and trackers evolve together; a correct displayed funding rate proves much less.

Static rules are immutable; live parameters are state

ChainRules supplies the outer cap through an Exchange-owned immutable context loaded at startup. Per-asset multipliers, interest rates and tracker maps continue to come from carried and mutated exchange state. Replacing those maps with a global environment setting would alter consensus behavior.

Funding changes require focused mainnet controls, shared engine tests, a bound release executable and affected forward checkpoints. A fresh cap fixture cannot extend historical binary evidence into every current sampling or stale-price branch.

Reported, aggregated and capped prices

Oracle reports, external references, marks and committed read-precompile views are different state surfaces. Mainnet 113 adds recovered cap and governance behavior to their existing lifecycle.

Name the price a caller consumes

The engine maintains oracle prices, external-perpetual references, mark prices and committed aggregates exposed to EVM reads. A funding sampler, liquidation planner and read precompile may intentionally consume different views. Replacing one with the latest convenient runtime map can change both valuation and historical execution.

Runtime generation counters can invalidate cached merged views without becoming serialized consensus fields. The cache is correct only when every authoritative mutation bumps the relevant generation and readers preserve the native committed-state boundary.

Report validation precedes storage and rebates

Reference-oracle admission checks the current voter set, update cooldown, scalar conversion and vector limits before storing a report. The source makes native rejection distinct from an unsupported or unreadable local state shape. A diagnostic inability to interpret a snapshot is not evidence that native rejected the action.

Successful storage then owns the report timestamp and related admission effects. Tests that seed only a reporter map omit important state such as the current voter set and carried cooldown; complete snapshot-like fixtures are needed.

Cap governance and mark refresh are separate writes

Current mainnet governance validates mark-cap updates as an ordered collection with duplicate-key protections and asset resolution. It validates the entire patch before applying it, so an invalid later entry cannot leave an earlier cap half-applied.

Changing caps updates cap state. Ordinary oracle maintenance applies the corresponding clamp to marks when it runs; the governance writer does not manufacture an immediate mark-price refresh. Deleting a cap and preserving a mark until the updater runs are therefore meaningful cases.

Freshness and endpoint proof remain independent

The current per-block sweep identifies stale main-oracle and stale HIP-3 mark wrappers as separate native intervals. An existing producer or admission proof cannot close those intervals solely because each concerns oracle state.

The latest handoff also records an unresolved oracle endpoint for an affected mainnet window. Its derivation and fresh replay belong to the acceptance work. Preserve prices, caps, timestamps and missing-value behavior together when examining the first checkpoint difference.

Three hash surfaces, three questions

The consensus app_hash, response-window resps.Hash and exchange ABCI tree commit to different data. Exact serialization and independent state evolution are required for each comparison.

The L1 half hashes ordered hexadecimal slot digests

The current mainnet W2 layout has 42 slots. Each mapped subsystem produces its exact serialized bytes and a Keccak-256 digest. The outer preimage is a compact MessagePack array of strings, each formatted as 0x followed by the slot's 64 hexadecimal characters, in slot order.

Keccak-256 of that array supplies the first 16 bytes of the 32-byte app_hash. Hashing an array of raw 32-byte digest values creates a different preimage. Legacy helper names and historical comments in the source do not override the concrete v3 constructor used by the current runtime.

The EVM half includes complete accumulators and counts

The EVM W1 preimage is a named MessagePack map containing accounts_hash, contracts_hash and storage_hash in that order. Each accumulator includes n_elements, n_bytes and its full 2,048-byte hash as a binary value. Its concise reduction alone cannot reconstruct this preimage.

The last 16 bytes of app_hash are the first 16 bytes of Keccak-256 over that named map. LtHash update and removal semantics must keep the full accumulator and both counts consistent as EVM execution changes accounts, code and storage.

L1 = Keccak256(MessagePack([hex(slot_0), ..., hex(slot_41)]))
EVM = Keccak256(named_MessagePack({accounts_hash, contracts_hash, storage_hash}))
app_hash = L1[0:16] || EVM[0:16]

Responses and the 60-field ABCI tree are separate commitments

resps.Hash is Keccak-256 of the exact MessagePack response window, grouped under the relevant transaction identifiers and containing the recovered response envelopes. An omitted envelope, different field order or different scalar representation changes this hash. It is not a hash of the entire exchange.

The exchange ABCI tree is a separate columnar diagnostic and digest surface with 60 current mainnet fields. Leaves feed primitive bytes into BLAKE3; branch encoding and the root abci_digest also use BLAKE3. Its in-memory schema can differ from snapshot serde order and includes EVM context unavailable from an L1 snapshot alone.

Certificates, round links and stake history

Certificate validity includes signed metadata, historical voting weights and chain linkage. Decoding a payload or recovering its signers does not alone establish a committed block.

Mainnet round links are signed fields

Current mainnet votes and QCs carry certified_parent_round and committed_round. The codec preserves them in block hashes and vote preimages. Startup rules explicitly select the round_links QC layout; state-hash vote layout and BFT QC layout are separate settings.

The carried fields cannot be inferred by subtracting one or two from the current round. Rounds can have gaps. Discarding those links, selecting an implicit layout or using a legacy signed preimage authenticates a different statement from the one the native producer supplied.

The committed round selects historical weights

QC verification selects stake history using the carried committed round, checks membership and weights, verifies signatures and validates round-link bounds. Leader prediction and proposer membership also use the corresponding history. Local execution progress is not a replacement stake-history key.

ClientBlocks commit admission verifies the supplied child and grandchild relationships and the final batch proof before engine mutation. A signer fixture exercises cryptographic bytes; a live epoch-weighted commit check additionally needs the right history and complete linkage.

Admission and local certificate formation have different proof obligations

hl-consensus contains the HyperBFT runtime, block store, collectors, round driver, leader inputs and signing-safety WAL. The experimental hl-bft-runtime interface has a classic adapter around that runtime. These source owners are concrete, but their presence is not a live validator acceptance event.

Current linked-QC formation remains explicitly unsupported until the native metadata producer is recovered. Receiving and verifying a linked certificate does not prove the ability to construct a correct local one. The project must preserve that frontier rather than fabricate parent and committed links.

Current node operation is receive and execute only

node-run boots local or fetched state, attaches a paired EVM executor and follows authenticated committed blocks. It never signs or broadcasts. This is the primary current node path described here; legacy gossip participation, devnet and differential-follow commands have separate scopes.

No completed mainnet live-sync certificate is claimed. Transport acknowledgement, received blocks and isolated signature controls are intermediate evidence. Continuous authenticated execution, correct stake transitions, exact state and operational failure handling all remain necessary.

HyperEVM inside the same node

HyperEVM adds a database-backed executor, L1 reads and delayed L1 intents. Correct replay must evolve its database and complete accumulators alongside HyperCore.

An executor needs the checkpoint database

hl-evm wraps revm with official checkpoint access, contract-code handling, precompile registration and transaction execution. The current mainnet configuration carries EVM chain ID 999. An L1 snapshot alone does not supply account storage and deployed bytecode needed to execute historical EVM transactions.

Bootstrap pairs the exchange's L1 height with an EVM checkpoint and its accumulator sidecar. A sidecar can seed hashes while leaving execution static; full forward validation must also attach a readable, complete database and apply actual EVM changes.

Read precompiles observe a defined L1 view

HyperCore read precompiles expose positions, balances, prices, staking and other L1 state to EVM contracts. Their provider must reproduce the committed view appropriate to the native EVM block, including defaults, missing rows, amount scales and return encoding.

Historical read-call archives can be useful comparison or replay artifacts, but their use changes the proof scope. A run that substitutes recorded read outputs does not independently certify every live read provider. Distinguish owned computation from an explicitly archived boundary oracle.

CoreWriter emits intents for later L1 execution

CoreWriter logs carry a sender and raw action payload. The EVM module unwraps the event, while shared action decoding and the engine's delayed-action path interpret and execute the L1 intent. Emission is not an immediate exchange mutation.

An EVM transaction can succeed while a later L1 intent fails admission or execution. Queue maturity, ordering, fee or admission effects and the resulting L1 response belong to the recovered delayed-action caller. A fresh-dev fallback contract must also be distinguished from the deployed runtime carried by an official checkpoint.

Database changes must reach all hash and publication views

The EVM state hash maintains account, contract and storage LtHash accumulators, each with complete bytes and element/byte counts. Deleting an account or storage item requires removal of the old contribution rather than only inserting a replacement or updating a reduced digest.

The October 9 storage audit identified a fallible post-commit code read and publication-order risks. Current source work addresses associated boundaries, but restart and fault behavior need separate validation. A matching receipt or sealed-block hash alone does not establish durable paired state.

Bridge votes and cross-layer transfers

External bridge finalization and HyperCore–HyperEVM movement are different paths. Each has its own authorization, queue and accounting lifecycle.

Separate the external bridge from the EVM boundary

Bridge2 tracks external deposit and withdrawal candidates, validator-set changes, votes, finished records and reserves. The internal HyperCore–HyperEVM route instead moves assets between exchange state and the EVM execution environment. Sharing a token or owner does not make these the same state machine.

An exact transfer must identify its source balance, destination, units, event identity and completion point. Crediting a convenient mirror early can pass a balance assertion while leaving vote trackers, reserves or the EVM accumulator inconsistent.

Deposit credit follows candidate-specific voting

Deposit votes bind an external event and candidate. The tracker counts eligible validators or hot voters through the appropriate quorum path and constrains votes for already finished deposits. Successful credit updates bridge balance and carried finished-deposit data through one owner.

Periodic pruning is observable work. It retains current voters, removes eligible candidate rows, refunds relevant admission units and updates per-voter event statistics. A no-credit or expired candidate can still affect trackers, so replay must follow the complete handler and maintenance lifecycle.

Withdrawals and validator sets carry their own authorization

Withdrawal handling maintains requests, signatures, finalization and reserve effects. Validator-set updates derive profiles and voting power from staking epochs, check the intended signing domain and require the relevant quorum. A current active set and a historical bridge epoch must not be interchanged.

Local state unavailability remains explicit. Missing epoch information, an unsupported domain or an unreadable carrier is not permission to fabricate a validator set, skip a signature or silently default a pending withdrawal to finished.

Queued native-token transfers are current mainnet behavior

The Mainnet 113 integration includes queued native-token transfers and their configured replay gate. Pending-transfer packets separately recover construction, compact-wire identity and processing behavior. A decoded queue record does not by itself prove every transfer or cleanup branch.

Cross-layer validation checks both exchange-side state and EVM effects, including supply, balances, reservations and accumulator removals or insertions. The public documentation exposes scoped evidence summaries rather than private operational host paths or wallet data.

Delegations, epochs and validator state

Staking simultaneously maintains economic balances, delegation history and consensus eligibility. Updates must keep its snapshot owners and EVM read views consistent.

Spendable stake includes pending withdrawals

Staking balances, delegated amounts and queued withdrawals are distinct quantities. The available balance used by the recovered registration and delegation checks is the carried staking balance less pending withdrawals, with the native saturating behavior. It is not a new spot deposit.

Delegation updates the user's balance, user-to-validator record, validator totals, historical current/minimum entries and current stake target. The one writer also updates projections consumed by EVM staking reads. A test seeded only in the visible balance map omits part of the state contract.

Epoch state supplies historical consensus context

Epoch advancement snapshots completed state, updates the current timestamp and maintains ordered historical entries under bounded retention rules. Active epoch selection and requested epoch identity are separate from the latest execution round.

Certificate verification, bridge validator sets and delegation history need the appropriate carried sample. Jailing, signer changes and delegation restrictions also affect eligibility. A flat current-validator list cannot replace all of these owners or their history.

Registration includes a profile, jail state and initial amount

The current native registration follow-up proves an outer payload with profile, unjailed and initial_wei. It corrects an earlier field attribution based on adjacent strings. Initial_wei is checked against existing spendable staking balance, and a nonzero accepted amount enters the shared self-delegation writer after registration.

The packet leaves compact node-IP encoding, insertion defaults and exceptional arithmetic or duration branches as finite frontiers. It also shows that some post-registration delegation errors are discarded by the outer native caller. Inventing atomic rollback would therefore be a semantic change, not a conservative default.

Reward and withdrawal maintenance are state transitions

Reward staging, distribution, stake decay and queued-withdrawal release use their own guards and carried timestamps. Their writers maintain c_staking state and the related projections rather than treating rewards as an API-only balance adjustment.

Existing historical packets remain useful for locating owners but do not automatically certify current Mainnet 113 branches. Keep current source mapping, native instruction recovery, focused tests and forward replay acceptance distinct when modifying staking or consensus inputs.

Complementary markets and settlement

Outcome markets combine paired tokens, ordinary spot books and collateral-backed mint or burn paths. Cross-book planning, publication and settlement require their own scoped evidence.

Complete sets connect the two sides

An outcome registry relates complementary side tokens, their spot pairs and collateral. A complete-set route links the two sides through one quote unit. The engine can therefore compare liquidity on the incoming side with liquidity on the complement after translating the complement's price and direction.

This adds state and financial effects beyond an ordinary spot match: side-token liabilities, collateral balances, owner holds and mapped fills. The exact mutation and response path must account for every leg, including an empty remainder or a self-owned resting order.

Cross-book selection is one planning problem

The complementary planner examines both relevant books in the incoming order's price terms, resolves ties according to the native branch and respects remaining size and spend capacity. A buy can mint paired sides and sell the complement; a sell can acquire the complement and burn a complete set.

Owned-order cancellation and ordinary placement must share the finite planner's chronology. Performing an additional independent own-order pre-scan can remove a different set of rows or reserve IDs in a different order, even if final market prices appear unchanged.

Reference admission merges the relevant book views

The published outcome-reference repair merges both outcome books before applying the unchanged minimum-value kernel. Its acceptance packet records affected and retained native windows with exact responses and checkpoints. It certifies the described admission repair rather than every outcome operation.

Outcome fees, holds and fill mapping can differ from ordinary spot assumptions. Do not infer one path's economic treatment from an external market analogy. Use the native route and its carried liabilities and collateral as the evidence boundary.

Deployment and settlement outlive the active book

Deployment maintains names, side metadata, token and pair registration, authorization and state limits. Settlement and question operations update outcome history and token state through governance-selected paths. An active-market matching proof cannot close those later lifecycle branches.

Current outcome packets split handler arithmetic, balance first-touch, cancellation and lifecycle closure into explicit scopes. The public explorer preserves those distinctions so a passed matching window cannot silently become a claim of complete question or settlement behavior.

BOLE reserves and liquidation outcomes

BOLE represents supplies and debts through reserve state and share-based accounting. Its current begin-block liquidation owner remains a separately audited implementation frontier.

Shares and token amounts are different carriers

Reserve accounting relates user supply and borrow shares to live reserve indices and token values. Supply, withdrawal, borrow and repayment change both user rows and reserve totals. Rounding a share conversion in the wrong direction can leave a residual unit or create a different empty-row state.

Portfolio collateral routing may withdraw supplied collateral, borrow against capacity, move funds into a class, then repay or resupply during release. These are ordered operations through canonical reserve writers, not a single collateral-balance assignment.

Qualification needs canonical valuation

The current native lending qualification values carried reserve positions and compares debt with successive capacity levels. Boundary equality belongs to the healthier class. Eligible owners are collected in a defined order before the mutation pass; later owner changes must not retroactively reclassify earlier carried qualification flags.

A failed valuation has its own native outcome, including pool-enabled state changes in the begin-block caller. An unsupported local schema must not be relabeled as that native refusal without evidence. Caller-specific terminal behavior matters as much as the valuation formula.

Evidence that survives the next repair

Native instructions, source binding, regression controls and runtime comparison form a provenance chain. Keeping those layers distinct makes claims reviewable and corrections possible.

One identified binary is the model

Every current native claim binds the Mainnet 113 hash and real ELF addresses. Earlier testnet or mainnet addresses can locate a research question but cannot establish current behavior without a new binding. A native binary is the specification for this reimplementation, including surprising failures and first-touch behavior.

Static recovery should be bounded to a function's instruction range, resolve indirect targets and decode every raw table entry, including duplicates. A failed or truncated decompilation proves a tool limit. It does not prove that native skips, inserts or rejects the operation.

Find the causal transition before proposing a rule

A response or tree mismatch identifies a difference, not its cause. Locate the earliest divergent state, decode its input, trace the native producer and inspect the complete relevant columns or bytes. A rule is accepted when native control flow or state pins it across the stated window, not because a score improves.

Do not add row insertion, rollback, owner exceptions or height gates to fit one checkpoint. Missing-row semantics, no-op publication, arithmetic order and admission charges are native questions. Controls should distinguish the recovered rule from plausible alternatives.

Bind proof packets and executables separately

The coverage inventory binds 49 source-file hashes from a fixed committed tree and references bounded native packets. The current strict-source check passes those mappings. Pending working-tree repairs remain outside that committed binding and need fresh review before inventory promotion.

Acceptance adds a frozen release executable, normal-library compilation provenance, input manifests, chain rules and native truth. A source path, successful unit test or saved log is one layer of that chain. Preserve original artifact hashes even when a public site presents a sanitized summary instead of raw host-bound data.

Publish useful boundaries with the result

The public site presents repository-derived explanations and selected textual evidence through its own reader. Host-only artifacts are identified as unavailable rather than turned into broken web links. Source anchors describe ownership without publishing private code or operational paths.

Every result should say its model, date, source binding, executed interval, supplied-truth coverage and unresolved dependencies. The current action table, semantic ledger, system audit and typed audit have different denominators. Keeping their scopes visible is what makes a fresh documentation surface trustworthy.
